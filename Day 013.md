# 100 Days of Cloud Azure - Day 013: SSH into an Azure Virtual Machine

## Scenario

The Nautilus DevOps team is configuring secure SSH access to an Azure Virtual Machine.

The goal is to allow the `root` user on the Azure client host to connect to the VM without a password by adding the client's SSH public key to the VM root user's `authorized_keys` file.

## Requirement

Configure SSH access with the following details:

- **Virtual Machine:** `datacenter-vm`
- **Region:** `West US`
- **Existing VM User:** `azureuser`
- **Target SSH User:** `root`
- **Client Public Key:** `/root/.ssh/id_rsa.pub`
- Add the public key to the VM root user's `authorized_keys`.
- Configure the correct SSH directory and file permissions.
- Verify passwordless SSH from the Azure client host to the VM as `root`.

## Dependency Path

The authentication path is:

```text
Azure Client
    │
    │ /root/.ssh/id_rsa
    │
    ▼
TCP/22
    │
    ▼
Azure VM
    │
    ▼
sshd
    │
    ▼
/root/.ssh/authorized_keys
    │
    ▼
Public Key Match
    │
    ▼
Passwordless Root SSH
```

## Implementation

### 1. Verify the VM

Using the Azure Portal, navigate to:

```text
Virtual machines → datacenter-vm
```

Verify that:

- The VM is in the `West US` region.
- The VM is running.
- The VM has network connectivity.
- SSH TCP port `22` is allowed by the applicable Network Security Group.

Record the VM's public IP address.

### 2. Verify the Client Public Key

From the Azure client host, verify that the required public key exists:

```bash
cat /root/.ssh/id_rsa.pub
```

The contents of this file are the public key that must be authorized on `datacenter-vm`.

> Only the `.pub` public key should be copied. The private key `/root/.ssh/id_rsa` must remain on the client and should never be copied to the VM.

### 3. Connect Using the Existing Azure User

Connect to the VM using the existing `azureuser` account:

```bash
ssh azureuser@<VM-PUBLIC-IP>
```

### 4. Configure Root SSH Authorization

Become root:

```bash
sudo -i
```

Create the root SSH directory if it does not already exist:

```bash
mkdir -p /root/.ssh
```

Set the correct directory permission:

```bash
chmod 700 /root/.ssh
```

Add the public key from:

```text
/root/.ssh/id_rsa.pub
```

on the **Azure client host** to:

```text
/root/.ssh/authorized_keys
```

on **datacenter-vm**.

Then configure the correct permissions:

```bash
chmod 600 /root/.ssh/authorized_keys
chown -R root:root /root/.ssh
```

## Verification Before Final Test

Verify the permissions:

```bash
ls -ld /root/.ssh
ls -l /root/.ssh/authorized_keys
```

Expected permissions should resemble:

```text
drwx------ root root /root/.ssh
-rw------- root root /root/.ssh/authorized_keys
```

Verify that the expected public key is present:

```bash
cat /root/.ssh/authorized_keys
```

## Final Validation

Exit back to the Azure client host:

```bash
exit
exit
```

Now test the original success criterion:

```bash
ssh root@<VM-PUBLIC-IP>
```

The connection should succeed using SSH public-key authentication without requesting the root user's password.

After connecting, verify the current identity:

```bash
whoami
```

Expected result:

```text
root
```

## Result

Passwordless SSH authentication was successfully configured between the Azure client host and `datacenter-vm`.

The final access path is:

```text
/root/.ssh/id_rsa
        ↓
SSH authentication
        ↓
datacenter-vm
        ↓
/root/.ssh/authorized_keys
        ↓
root login successful
```

## Key Takeaways

- SSH key authentication uses a **private/public key pair**.
- The private key remains securely on the client.
- The corresponding public key is placed in the remote user's `authorized_keys` file.
- `~/.ssh` should normally have `700` permissions.
- `authorized_keys` should normally have `600` permissions.
- File ownership and permissions matter because `sshd` can reject insecure SSH configurations.
- NSG access to TCP/22 and successful SSH authentication are separate layers: the network must first permit the connection before SSH can authenticate the user.
- Passwordless SSH should always be validated from the original client rather than assuming that adding the key was sufficient.
- Direct root SSH access carries additional security risk and should generally be restricted in production environments unless there is a specific operational requirement.
