# 100 Days of Cloud Azure - Day 025: Expanding and Managing Disk Storage

## Scenario

The Nautilus DevOps team needs to increase the storage capacity of an existing Azure Virtual Machine to support growing workloads.

The task involves two separate storage operations:

1. Expand the existing VM OS disk from `32 GiB` to `64 GiB`.
2. Create and attach a new `64 GiB` Standard HDD data disk and mount it inside Linux at `/mnt/devops-disk`.

## Requirement

Configure the existing environment with the following specifications:

- **Virtual Machine:** `devops-vm`
- **Existing Disk:** Expand from `32 GiB` to `64 GiB`
- **New Data Disk Name:** `devops-disk`
- **Data Disk Size:** `64 GiB`
- **Data Disk Type:** Standard HDD (`Standard_LRS`)
- **Mount Point:** `/mnt/devops-disk`

The final storage layout should resemble:

```text
devops-vm
│
├── OS Disk
│   └── 64 GiB
│
└── devops-disk
    ├── Standard HDD
    ├── 64 GiB
    └── /mnt/devops-disk
```

## Implementation

### 1. Verify the Existing VM

In the Azure Portal, navigate to:

```text
Virtual machines → devops-vm
```

Before making changes, verify:

- The VM exists and is healthy.
- The current OS disk size is `32 GiB`.
- No existing data disk named `devops-disk` is already attached.

This establishes the initial state before modifying storage.

---

## 2. Expand the Existing OS Disk

Navigate to:

```text
devops-vm
→ Settings
→ Disks
→ OS disk
```

Open the existing OS disk and navigate to:

```text
Settings → Size + performance
```

Change the disk size from:

```text
32 GiB
```

to:

```text
64 GiB
```

Save the change and wait for Azure to complete the disk resize.

> Increasing the Azure managed disk changes the underlying block device capacity. The guest operating system may still require its partition and filesystem to be extended before Linux can use the additional space.

---

## 3. Create and Attach the Data Disk

Return to:

```text
Virtual machines
→ devops-vm
→ Settings
→ Disks
```

Select:

```text
Create and attach a new disk
```

Configure:

```text
Disk name:     devops-disk
Storage type:  Standard HDD
Disk SKU:      Standard_LRS
Size:          64 GiB
```

Save the VM disk configuration.

Wait until Azure reports that the update has completed successfully.

## Verification Before Linux Configuration

Confirm that `devops-vm` now shows:

```text
OS Disk:    64 GiB
Data Disk:  devops-disk
             └── 64 GiB Standard HDD
```

At this stage, the data disk is attached at the Azure infrastructure layer, but it is not necessarily ready for filesystem use inside Linux.

---

## 4. Connect to the VM

SSH into `devops-vm` using its configured administrative account:

```bash
ssh azureuser@<PUBLIC-IP>
```

Verify the available block devices:

```bash
lsblk
```

Identify the newly attached `64 GiB` data disk.

For example, it may appear as:

```text
sdc    64G disk
```

> Always identify the disk using `lsblk` before partitioning or formatting. Device names can vary between systems, so do not assume the new disk will always be `/dev/sdc`.

---

## 5. Check Whether the Disk Contains Existing Data

Before formatting anything, inspect the new device:

```bash
sudo lsblk -f
```

Optionally:

```bash
sudo blkid
```

If the new disk is blank and contains no required filesystem or data, proceed with filesystem creation.

This verification is important because running `mkfs` against the wrong disk would destroy existing data.

---

## 6. Create a Filesystem

Assuming the new blank disk was identified as `/dev/sdc`, create an XFS filesystem:

```bash
sudo mkfs.xfs /dev/sdc
```

Verify:

```bash
sudo lsblk -f
```

The device should now report an XFS filesystem.

---

## 7. Create the Mount Point

Create the required directory:

```bash
sudo mkdir -p /mnt/devops-disk
```

Mount the filesystem:

```bash
sudo mount /dev/sdc /mnt/devops-disk
```

Verify:

```bash
df -h /mnt/devops-disk
```

The new filesystem should show approximately `64 GiB` of capacity.

---

## 8. Configure Persistent Mounting

A manual `mount` does not survive a reboot, so configure `/etc/fstab`.

Retrieve the filesystem UUID:

```bash
sudo blkid /dev/sdc
```

Example:

```text
/dev/sdc: UUID="<UUID>" TYPE="xfs"
```

Back up the existing filesystem table:

```bash
sudo cp /etc/fstab /etc/fstab.bak
```

Add the filesystem using its UUID:

```text
UUID=<UUID>  /mnt/devops-disk  xfs  defaults,nofail  0  2
```

Using the UUID is preferable to relying on `/dev/sdc`, because Linux device names can change.

---

## 9. Validate the Persistent Mount

Before rebooting, validate the `/etc/fstab` configuration.

Unmount the disk:

```bash
sudo umount /mnt/devops-disk
```

Test all configured mounts:

```bash
sudo mount -a
```

Verify:

```bash
findmnt /mnt/devops-disk
```

Also verify:

```bash
df -h /mnt/devops-disk
```

If `mount -a` succeeds and the filesystem appears at `/mnt/devops-disk`, the persistent mount configuration is valid.

## Verification

Verify the block-device layout:

```bash
lsblk
```

Verify filesystems:

```bash
lsblk -f
```

Verify the data-disk mount:

```bash
findmnt /mnt/devops-disk
```

Verify available capacity:

```bash
df -h
```

The final state should confirm:

```text
OS Disk
└── Expanded to 64 GiB

devops-disk
├── 64 GiB
├── Standard HDD / Standard_LRS
├── Filesystem created
└── Mounted at /mnt/devops-disk
```

Finally, run the KodeKloud challenge validation.

## Result

The storage configuration of `devops-vm` was successfully expanded:

```text
Azure
│
└── devops-vm
    │
    ├── OS Disk
    │   └── 32 GiB → 64 GiB
    │
    └── devops-disk
        ├── Standard_LRS
        └── 64 GiB
             │
             ▼
          Linux
             │
             ├── XFS filesystem
             ├── /etc/fstab
             └── /mnt/devops-disk
```

The VM now has additional OS disk capacity and a separate persistent `64 GiB` data disk mounted at the required location.

## Key Takeaways

- Azure disk attachment and Linux filesystem configuration are separate layers.
- Increasing an Azure managed disk does not automatically guarantee that the Linux partition and filesystem use the additional capacity.
- A newly attached blank data disk must normally be identified, formatted, and mounted before applications can use it.
- Always inspect a disk before running `mkfs`; formatting the wrong device can permanently destroy data.
- `lsblk`, `lsblk -f`, `blkid`, `findmnt`, and `df` provide evidence at different layers of the Linux storage stack.
- `/etc/fstab` makes filesystem mounts persistent across reboots.
- UUID-based `/etc/fstab` entries are safer than relying on potentially changing `/dev/sdX` device names.
- `mount -a` is an important validation step before rebooting after modifying `/etc/fstab`.
- Storage changes should be validated from both perspectives: Azure must show the correct managed disks, and Linux must show the expected usable filesystems and mount points.
