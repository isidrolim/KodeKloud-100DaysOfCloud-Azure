# 100 Days of Cloud Azure - Day 015: Create and Configure Network Security Group (NSG) in Azure

## Scenario

The Nautilus DevOps team is continuing its incremental migration to Microsoft Azure. As part of securing the Azure network infrastructure, a Network Security Group (NSG) needs to be created with inbound rules that permit HTTP and SSH traffic.

## Requirement

Create and configure an Azure Network Security Group with the following settings:

- **NSG Name:** `devops-nsg`
- **Method:** Azure Portal (GUI)

Configure two inbound security rules:

### HTTP Rule

```text
Name:             Allow-HTTP
Source:           0.0.0.0/0
Service:          HTTP
Destination Port: 80
Protocol:         TCP
Action:           Allow
Direction:        Inbound
```

### SSH Rule

```text
Name:             Allow-SSH
Source:           0.0.0.0/0
Service:          SSH
Destination Port: 22
Protocol:         TCP
Action:           Allow
Direction:        Inbound
```

## Implementation

### 1. Create the Network Security Group

1. Sign in to the **Azure Portal**.
2. Search for:

   ```text
   Network security groups
   ```

3. Open **Network security groups** and click:

   ```text
   Create
   ```

4. Under **Basics**:
   - Select the existing subscription.
   - Select the existing resource group.
   - Enter the NSG name:

   ```text
   devops-nsg
   ```

5. Select the required region based on the existing lab resources.
6. Click:

   ```text
   Review + create
   ```

7. Confirm validation succeeds and click:

   ```text
   Create
   ```

8. Wait for the NSG deployment to complete.

---

## Configure the HTTP Inbound Rule

1. Open:

   ```text
   Network security groups → devops-nsg
   ```

2. Navigate to:

   ```text
   Settings → Inbound security rules
   ```

3. Click:

   ```text
   Add
   ```

4. Configure the rule:

   ```text
   Source:                   IP Addresses
   Source IP addresses:      0.0.0.0/0
   Source port ranges:       *
   Destination:              Any
   Service:                  HTTP
   Destination port:         80
   Protocol:                 TCP
   Action:                   Allow
   Name:                     Allow-HTTP
   ```

5. Ensure the rule has a unique priority.
6. Click **Add**.

---

## Configure the SSH Inbound Rule

1. From **Inbound security rules**, click:

   ```text
   Add
   ```

2. Configure the second rule:

   ```text
   Source:                   IP Addresses
   Source IP addresses:      0.0.0.0/0
   Source port ranges:       *
   Destination:              Any
   Service:                  SSH
   Destination port:         22
   Protocol:                 TCP
   Action:                   Allow
   Name:                     Allow-SSH
   ```

3. Assign a different priority from the HTTP rule.
4. Click **Add**.

Verify that both custom inbound rules exist.

The configuration should resemble:

| Name | Port | Protocol | Source | Action |
|---|---:|---|---|---|
| `Allow-HTTP` | 80 | TCP | `0.0.0.0/0` | Allow |
| `Allow-SSH` | 22 | TCP | `0.0.0.0/0` | Allow |

Confirm that:

- `devops-nsg` exists.
- `Allow-HTTP` permits TCP port `80`.
- `Allow-SSH` permits TCP port `22`.
- Both rules use `0.0.0.0/0` as their source.
- Both rules have the `Allow` action.
- Each custom rule has a unique priority.

The required HTTP and SSH inbound access rules are now configured.

## Key Takeaways

- Azure Network Security Groups act as stateful network traffic filters for Azure resources.
- NSG rules evaluate traffic using properties such as source, destination, protocol, port, priority, and action.
- Lower priority numbers are processed before higher priority numbers.
- HTTP normally uses TCP port `80`, while SSH normally uses TCP port `22`.
- `0.0.0.0/0` represents all IPv4 source addresses.
- Allowing SSH from `0.0.0.0/0` exposes TCP/22 to the entire internet and should generally be avoided in production.
- Production SSH access should normally be restricted to approved source networks or provided through controlled access mechanisms such as Azure Bastion.
- Creating an NSG and creating rules does not by itself protect a workload—the NSG must also be associated with the appropriate subnet or network interface when required by the architecture.
