# 100 Days of Cloud Azure - Day 019: Convert Public Azure Blob Container to Private

## Scenario

The Nautilus DevOps team has been using Azure Blob Storage to manage application data.

One of the existing Blob containers currently allows public access, but the data now needs to be restricted for internal use only. The task is to change the container from public to private without modifying another existing private container.

## Requirement

Use the following existing Azure resources:

- **Storage Account:** `devopsst902220240`
- **Region:** `East US`
- **Container to Modify:** `devops-container-902220240`
- **Existing Private Container:** `devops-priv-902220240`
- **Required Access Level:** Private
- **Method:** Azure Portal (GUI)

The goal is:

```text
Before
├── devops-container-902220240 → Public
└── devops-priv-902220240      → Private

After
├── devops-container-902220240 → Private
└── devops-priv-902220240      → Private (unchanged)
```

## Implementation

### 1. Locate the Storage Account

1. Sign in to the **Azure Portal**.

2. Search for:

   ```text
   Storage accounts
   ```

3. Open the existing storage account:

   ```text
   devopsst902220240
   ```

4. Verify that the storage account is associated with the required:

   ```text
   East US
   ```

   region.

---

## 2. Inspect the Existing Containers

Navigate to:

```text
Data storage → Containers
```

Verify that both required containers exist:

```text
devops-container-902220240
devops-priv-902220240
```

Before making any changes, identify their current access levels.

The expected initial state is:

```text
devops-container-902220240 → Public
devops-priv-902220240      → Private
```

Only `devops-container-902220240` should be modified.

---

## 3. Change the Public Container to Private

Select:

```text
devops-container-902220240
```

Open the container's access-level configuration using:

```text
Change access level
```

Change the anonymous access level to:

```text
Private (no anonymous access)
```

Save/apply the change.

Do **not** modify:

```text
devops-priv-902220240
```

because it is already configured correctly.

## Verification

Return to:

```text
Storage accounts
    ↓
devopsst902220240
    ↓
Data storage
    ↓
Containers
```

Verify the final state:

```text
Container                       Access Level
------------------------------  -----------------------------
devops-container-902220240      Private (no anonymous access)
devops-priv-902220240           Private (no anonymous access)
```

Confirm specifically that:

- `devops-container-902220240` no longer allows anonymous public access.
- `devops-priv-902220240` remains unchanged.
- Both containers still exist.
- No container data was deleted during the configuration change.

Finally, run the KodeKloud challenge validation.

## Result

The existing public Azure Blob container was successfully converted to private access:

```text
devopsst902220240
│
├── devops-container-902220240
│       └── Private ✅
│
└── devops-priv-902220240
        └── Private ✅ (unchanged)
```

Anonymous access to `devops-container-902220240` is now disabled while the existing private container remains unchanged.

## Key Takeaways

- Azure Blob containers can have different anonymous access levels within the same storage account.
- **Private** prevents anonymous access to both the container and its blobs.
- Changing a container from public to private changes its access configuration; it does not require recreating the container or deleting its data.
- Existing authenticated access can still be provided through supported Azure authentication and authorization mechanisms.
- Before changing production resources, always identify the exact target and verify the existing state to avoid modifying resources that are already correctly configured.
- Public access should generally be disabled unless anonymous access is an explicit application or business requirement.
- This task demonstrates an important production principle: make the **smallest required change** and leave correctly configured resources untouched.
